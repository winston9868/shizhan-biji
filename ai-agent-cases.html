复盘方法论

踩过的坑，才是真资产。以下框架适用于所有 AI Agent 任务类案例。

📐 通用复盘框架（四象限法）

每个 AI Agent 任务跑完后，按这四个维度做一次复盘，比单纯看输出质量有用得多：

✅ 该做的事

  • 先跑最小验证：先用最简提示词确认 Skill 能调通，再加约束条件逐步收敛
  • 留原始快照：首次运行的完整输出截图/文本存一份，后续对比才有基准线
  • 定义验收清单：动手前就写好「怎么算成功」，避免事后找补标准
  • 记录环境版本：Skill 版本、模型版本、执行时间 —— 同一提示词在不同时期可能产出不同结果
  • 测边界情况：空结果、超时、格式异常时系统怎么表现？提前踩坑比线上翻车好

❌ 别做的事

  • 别把首跑当常态：第一次运气好不代表稳定，至少跑 3 次看方差
  • 别跳过安全检查：外部 Skill 再好用也要审来源、权限、脚本内容
  • 别默认输出可信：资讯类 Skill 的摘要可能遗漏或夸大，关键结论必须点开原链接核实
  • 别一次性加太多约束：提示词从粗到精迭代，一步到位容易互相矛盾
  • 别忽略成本感知：单次免费不等于自动化后免费，高频任务要算 token 账

📊 关键指标

指标含义目标值
通过率验收清单全通过的次数 / 总运行次数≥ 90%
稳定性相同提示词多次运行的结构一致性≥ 85%
时效性从触发到拿到结果的耗时< 3 min
可核查率带来源链接的条目占比= 100%
复用成本换一个主题重新跑的工作量< 5 min

🔄 复盘 SOP

  1. 记录：保存完整提示词 + 完整输出 + 运行时间
  2. 对照：逐条过验收清单，标记通过/失败/待定
  3. 分析：失败的根因是什么？（提示词模糊 / Skill 限制 / 数据噪声 / 格式漂移）
  4. 优化：改提示词 / 加后处理 / 换参数，只改一个变量再跑
  5. 固化：稳定后写成模板，交给自动化或团队复用

🔥 从案例一 & 案例二中提炼的踩坑经验

P0 致命直接用摘要做对外发布 → AIHot 是聚合源不是事实核查器，热点数字可能来自单一不可靠信源。必须点开原链接交叉验证。
P1 严重提示词太粗导致每次格式不同 → 「总结 AI 新闻」可能这次出列表、下次出段落。固定输出结构（编号+字段）才能对接下游自动化。
P1 严重不检查 Skill 是否真正被调用 → 安装成功 ≠ 当前工作区可见。跑完第一句就让 WorkBuddy 回报实际调用的是哪个 Skill。
P2 一般时间范围设太大导致信息过载 → 「最近 30 天」可能返回 50+ 条，核心信号被淹没。日常监控建议 7 天以内。
P2 一般忽略去重导致同一事件反复出现 > 同一发布会被 5 个媒体各报一次 = 占了 5 条额度。提示词里必须显式要求「合并重复事件」。
P0 致命虚构演示数据直接用于真实投递 → 案例二明确标注"虚构候选人"，但实际使用时若忘记替换为真实数据，后果严重。必须养成"发送前逐字段核对"的习惯，尤其是联系方式和公司名称。
P1 严重模板选择纠结浪费时间 → 12 套模板各有风格，首次使用可能反复切换预览。建议：先选默认模板跑通流程，满意内容后再换模板调整外观——内容和排版是两件事。
P2 一般多轮迭代后格式漂移 → 连续修改 3-4 轮后（加经历、调间距、换重点），最终版可能与初始模板风格偏离较大。每 2 轮做一次"全量预览检查"，确保整体一致性。
P1 严重IP 白名单遗漏导致推送失败 → 配置凭证前务必先把本机公网 IP 加入公众号后台白名单（用 WiFi 固定 IP，别用热点）；否则第一步就报「IP 不在白名单」。
P2 一般frontmatter 缺 cover 被拒 → wenyan-cli 强制要求 title 和 cover 缺一不可，封面图建议用绝对路径，避免相对路径解析失败。
P1 严重连接器授权过期读不到知识库 → 定期确认 ima 连接器授权状态、ima 客户端同账号登录，否则 WorkBuddy 读不到内容，梳理无从谈起。
P2 一般提示词太泛导致梳理不深 → 在提示词里明确分类维度、提取粒度和输出格式，提示词越具体，结构化结果越可控。
P0 致命共享 tween 对象导致动画跳变 → GSAP 多个 tween 操作同一变量时，必须用共享对象而非各自创建临时对象，否则起始值=终值无渐变。
P1 严重依赖在线 CDN / 大文件踩坑 → 媒体走本地、GitHub 注意 50MB 警告与 LFS；push 前 .gitignore 排除 node_modules 与工作区数据。
P2 一般一轮改太多难以定位 → 每次只反馈一个最突出的问题，避免同时改多处导致难以判断哪步生效。
P1 严重口径被默默猜错 → 先摸底再动手；缺年日期、品类近义词等处理假设必须写入「数据质量报告」由人确认，不擅自假定。
P1 严重看板「点完只剩一根柱」 → 被点击维度自身也被收窄。改造为被点维度图忽略自身筛选、始终完整显示并置顶高亮选中项。
P2 一般在线 CDN 导致离线打不开 → ECharts 等依赖库下载到本地，保证双击离线可用，避免断网或分享后白屏。
P0 致命文本挖掘推导指标当官方口径 → 叙事强度、数字化投入估算等属文本挖掘推导，非公司披露口径，引用前须与年报原文核对。
P1 严重下载触发限制 / 混入干扰文件 → 按公告类别过滤去重、控制访问频率；剔除年报摘要、英文版、更正公告等干扰文件。
P2 一般披露口径中途变化 → 不同口径的数字不要直接连成趋势线，对切换点做显式标注，避免误导。
P0 致命Chart.js CDN 加载失败导致白屏 → 老田本机浏览器 jsdelivr 不通，必须把 Chart.js 下载内嵌进 HTML，交付单文件离线可用版本。教训：任何外部依赖在交付前先确认本机可达性。
P1 严重PPTX 图表区域占比失衡 → Slide 2/3 图表宽度仅占 58%/54%，左侧视觉空白。解法：图表区域不低于 60%，右侧结论卡收窄至 30% 以下，中间留 0.2" 呼吸缝。「反馈→定位参数→修复→重生成」的循环比手工快 10 倍。
P1 严重硬编码百分比在后续更新中对不上 → PPTX 结论中「东北仅占 4.0%」等数字是写死的，数据变化后成为错误信息。解法：用 Python 从真实数据计算百分比后注入 JSON，Node.js 脚本从 JSON 读值而非硬编码。
P2 一般自动化 CSV 文件名匹配规则过窄 → 初始正则只匹配 `_数字月.csv`，测试 CSV 命名「模拟」无法命中。解法：放宽匹配到 `*区域销售数据_*.csv`，同时按修改时间排序兜底，优先取最新。

结论与建议

🏆 案例共性结论

1. AI 信息收集类任务，Skill 化是分水岭

通用大模型能「回答问题」但不能「提供带来源的最新资讯」。专门的信息 Skill（如 AIHot）填补了这个空白 —— 它的本质是实时检索 + 结构化聚合 + 来源追溯三层能力的组合。

2. 提示词精度直接决定产出可用性

同一个 Skill，「总结 AI 新闻」和「四要素齐全的五步提示词」的产出质量差距巨大。好的提示词 = 时间范围 + 关注主题 + 筛选标准 + 输出格式，缺一不可。

3. 先跑通单次，再谈自动化

案例一的合理节奏是：安装 Skill → 粗提示词验证 → 精提示词收敛 → 跑 3 次确认稳定 → 写成模板 → 接自动化。跳过中间步骤直接上自动化，调试成本反而更高。

4. 可核查性是资讯类任务的底线

不带来源链接的 AI 摘要只能当「线索」，不能当「结论」。每条信息都能追溯到原始报道，才是可以在工作中依赖的标准。

5. 文档生成类任务，Skill = 排版引擎 + 内容整理器

案例二揭示了一个不同维度的价值：AI Skill 不只是信息工具，更是"排版引擎"。它把"写内容 + 选模板 + 调布局 + 导出多格式"四步压缩成一步。核心优势不是"写得更好"，而是改起来更快——迭代修改不破坏已有排版，这是传统 Word/PPT 做不到的。

6. 凭证类任务：门槛全在第一次配置

案例三卡在公众号凭证 + IP 白名单，案例四卡在 ima 连接器授权 —— 两者首次配置都比正文耗时。判断这类任务值不值得做，看的不是首次成本，而是未来会重复多少次：一次性需求不划算，周更/日更的场景第二次就回本。

7. 知识库的价值不在「存」，在「加工闭环」

案例四把 ima 用成「存 → 加工 → 回传 → 再生长」的循环，而不是收藏夹。碎片内容只有被重组成结构化体系再写回知识库，才会从存了没看变成能被检索复用。缺了「回传」这一步，知识库就是个只进不出的黑洞。

8. 创意类任务靠迭代收敛，不靠一次说清

案例五用了 17 轮反馈才定稿。视觉/前端需求天然难以一次描述准确，正确姿势是先跑出可见版本，再逐轮微调，且每轮只改一个维度（先结构 → 再动效 → 最后配色）。一次性堆砌全部要求，反而会让每轮返工都推倒重来。

9. 数据清洗要先定规则，再留质量报告

案例六面对 119 份格式各异的门店表，关键动作不是「让 AI 清洗」，而是先显式约定清洗规则（字段映射 / 空值处理 / 异常值口径），并要求产出附带质量报告。有报告才能核查，保留活公式才能追溯到原始单元格 —— 这是数据类任务可信的前提。

10. 复杂研究适合「专家团并行拆解」

案例七把十年年报拆给多个角色并行处理再汇总。单条提示词扛不住这种量级，正确做法是拆成角色 + 明确交付物 + 过程产物落盘。落盘尤其关键：中间脚本和数据留下来，结论才可复现，而不是一次性的黑箱输出。

🧭 八个案例的共同骨架

场景差异很大（资讯、简历、公众号、知识库、动画、数据、投研），但跑通路径高度一致：

① 选对能力（Skill / 连接器 / 专家团）→② 提示词写足四要素→③ 先跑通单次→④ 对照验收清单→⑤ 模板化 / 自动化复用

跳过第 ③ 步直接上自动化，或跳过第 ④ 步直接对外交付，是八个案例里代价最高的两种走法。

适合 ✅谨慎 ⚠️不适合 ❌
  • 每日/每周行业资讯汇总
  • 竞品动态持续跟踪
  • 学术/技术论文前沿扫描
  • 舆情监测与热点发现
  • 任何「多源→聚合→结构化」的信息流
  • 文档/简历/报告一键生成与迭代修改
  • 公众号/多平台内容的排版与发布（案例三）
  • 碎片知识的结构化沉淀与复用（案例四）
  • 作品集/展示类前端动画（案例五）
  • 多表合并清洗 + 交互式看板（案例六）
  • 公开资料驱动的深度研究报告（案例七）
  • 需要实时秒级更新的场景（用 RSS / API 更合适）
  • 高度敏感的合规/法律信息（须人工审核）
  • 小众领域（Skill 可能覆盖不足）
  • 依赖第三方凭证/IP 白名单的发布类任务（配置门槛高，一次性需求不划算）
  • 需要设计师级审美定稿的视觉项目（AI 出草稿，定稿仍需人把关）
  • 跨系统数据同步（连接器授权会过期，需定期复检）
  • 需要 100% 准确率的财务/法务数据
  • 强交互式探索（需要反复追问深挖）
  • 离线环境（无法访问外部 Skill）
  • 实时交易/秒级刷新的监控看板（本地静态产物做不到）
  • 依赖未公开信息的投研判断（只有公开年报支撑不了）
  • 把 AI 生成的研究结论直接当决策依据（必须回原文核对）
